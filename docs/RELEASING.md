# Releasing

**Every shipment gets a GitHub release.** One tag, one artifact, one enumeration of
exactly what an operator will install. This is the standing practice for this repo,
not a per-upgrade decision.

## Why

The deliverable here is not source code — it is a 330 MB bundle of RPMs and scripts
that gets hand-carried onto disconnected production servers. That creates problems a
git tag alone does not solve:

- **The RPMs are not in git.** A tag tells you which *scripts* shipped; it says
  nothing about which *packages* an operator actually installed. The release notes
  enumerate both.
- **An air-gapped operator cannot rebuild the bundle.** They have no internet.
  Whatever file they were handed is the whole world. It must be downloadable, whole,
  from one URL.
- **"Which bundle is on that node?" is an incident question.** When a node misbehaves
  months later, the answer has to be a checksum you can look up, not an inference
  from timestamps.
- **Upstream moves.** `download.docker.com` publishes new builds and eventually
  retires old ones. A bundle built today is not reproducible from the same script
  next year. The artifact *is* the record.

## Tag scheme

```
v<TARGET_DOCKER_VERSION>-<BUNDLE_REVISION>
```

- `v29.6.2-1` — first bundle shipping Docker 29.6.2
- `v29.6.2-2` — same Docker version, rebuilt (script fix, added package, corrected
  rollback set)

The Docker version is what operators and change tickets talk about, so it leads. The
revision covers the real case where the same target ships twice because something
*else* in the bundle changed.

## Cutting a release

```bash
tests/vm/bootstrap-vm.sh          # once, if the VM does not exist
tools/make-release.sh v29.6.2-1   # add --draft to review before publishing
```

`make-release.sh` refuses to proceed unless:

- the working tree is clean
- every local commit is pushed
- the tag and release do not already exist
- `tests/static-checks.sh` passes

It then **rebuilds the bundle from the current checkout** — it never reuses whatever
happens to be sitting in the VM. Shipping a bundle whose embedded scripts predate the
tag is precisely the failure this guards against. (`--reuse-bundle` exists for
retrying a failed upload; do not use it to cut a new release.)

The artifact is copied out of the VM and its SHA-256 verified on both sides before
anything is uploaded.

## What the release notes contain

Generated by `tools/vm-bundle-manifest.sh` from **RPM metadata**, never filenames — a
release note enumerating versions is a claim about what gets installed, so it comes
from the packages themselves:

- every package in `rhel8/`, `rhel9/`, `rollback-rhel8/`, `rollback-rhel9/`, `nvidia/`
  with name, version, release and arch
- every script in the bundle with its `VERSION`
- artifact size, SHA-256 and RPM count
- the commit it was built from
- the current testing status from `docs/TEST-PLAN.md`

## Verifying a release

```bash
gh release download v29.6.2-1
sha256sum -c <<< '<sha from the release notes>  docker-upgrade-bundle-v29.6.2-1.tar.gz'
```

The bundle's own RPM digests are checked again by `upgrade-docker.sh` phase 0 on the
target node, so a corrupted transfer fails before anything is stopped.

**Digests prove integrity, not authenticity.** In a regulated environment, also verify Docker's GPG
signatures against a pinned key fingerprint at bundle-build time — see
`docs/TEST-PLAN.md` §1.11.

## Housekeeping

- `dist/` is gitignored. Artifacts live on the release, not in the tree.
- Do not delete old releases. A node running an old bundle needs its rollback set to
  remain downloadable.
- If a release is found to be bad, cut a new revision and note the reason. Do not
  quietly replace the artifact on an existing tag — anyone who already downloaded it
  would have no way to tell.
