# Docker 29.1.5 → 29.6.2 Upgrade Retarget

> **SUPERSEDED — historical record.** This design targeted docker-ce 29.6.2 /
> containerd.io 2.2.6, a bundle that was built but never deployed. On 2026-08-19 the
> upgrade was retargeted to **29.7.2 / containerd.io 2.3.3**, which crosses the
> containerd 2.2 → 2.3 config-version boundary (3 → 4) that this document explicitly
> assumed away. Do not use the versions or the "stays inside containerd 2.2.x"
> rationale below as current guidance — see `CLAUDE.md` and `README.md`.

**Date:** 2026-07-28
**Status:** Approved

## Context

The cluster is currently running docker-ce 29.1.5 with containerd.io 2.2.1, deployed
by the existing scripts in this repo. The goal is to move it to the latest packages
available on `download.docker.com` as of today.

This is materially different from the upgrade these scripts were originally written
for. The 28.5.1 → 29.1.5 work crossed a containerd **major** boundary (1.7 → 2.x),
which forced a config-format migration, a filesystem compatibility requirement, and
orphaned-network cleanup. The 29.1.5 → 29.6.2 move stays inside containerd 2.2.x.
Most of that machinery is now inert at best and harmful at worst.

## Target versions

Confirmed present in `download.docker.com/linux/rhel/{8,9}/x86_64/stable/Packages/`
on 2026-07-28. Both el8 and el9 builds exist at these versions.

| Package | From | To |
|---|---|---|
| docker-ce | 29.1.5 | **29.6.2** |
| docker-ce-cli | 29.1.5 | **29.6.2** |
| containerd.io | 2.2.1 | **2.2.6** |
| docker-buildx-plugin | 0.30.1 | **0.35.0** |
| docker-compose-plugin | 5.0.1 | **5.3.1** |

Rollback target becomes **29.1.5 / 2.2.1** — the known-good state the cluster is on
today. The 28.5.1 / 1.7.29 rollback set is dropped: reaching it would require a
containerd major downgrade across the whole cluster simultaneously, which is not a
realistic emergency action.

`docker-buildx-plugin` and `docker-compose-plugin` continue to version independently
of docker-ce and are not pinned to it.

## Changes by file

### `upgrade-docker.sh` → v2.0.0

Version constants retargeted, plus three structural changes:

**Phase 4.5 (orphaned network cleanup) is removed**, extracted verbatim into a new
standalone `clean-swarm-networks.sh`. The phase number is left vacant so phases 5–10
keep their existing identities.

Rationale: the VXLAN/netns/`local-kv.db` wipe fixed orphaned state left when
containerd was swapped out from under a running dockerd across the major boundary.
Within 2.2.x the ordered shutdown in phase 4 stops the daemon cleanly, so there is
no orphaned state to collect. The wipe is itself a destructive reset of daemon
network state, and the 29.x line has been actively improving overlay convergence
(29.0.0 fixed NetworkDB "entries stuck deleted"; 29.5.0 fixed stale VIP DNS records
during rolling updates). Running it unconditionally would guarantee a network-state
reset on every node to insure against a failure mode specific to the major swap.

**`check_xfs_ftype()` and the phase-6 interactive relocation loop are removed
entirely.** containerd 2.x's XFS `ftype=1` requirement is real, but any node running
2.2.1 today has already satisfied it — the check cannot fire usefully and the
relocation prompt can only confuse an operator mid-upgrade. A comment in phase 6
points at `upgrade-docker.sh` v1.2.3 in git history for whenever a future containerd
major upgrade needs the logic back.

**Phase 6 becomes "Verify containerd config"** and no longer runs
`containerd config default > /etc/containerd/config.toml`.

Rationale: this was the sharpest hazard in the retarget. 2.2.1 and 2.2.6 share
config v3, so there is nothing to migrate — but regenerating discards the file's
contents, including a relocated `root =` path on any node that took the ftype=0
escape hatch during the previous upgrade, plus any registry-mirror or runtime
configuration. Such a node would be silently repointed at an empty
`/var/lib/containerd`.

The phase now generates a default config only if the file is absent; otherwise it
leaves the file alone, reads `root =` for reporting, and ensures that directory
exists. No separate config parse check is added — phase 8 already polls
`ctr version` and `ctr snapshots --snapshotter overlayfs ls`, and a malformed config
means containerd never becomes responsive.

Phases 1 (Swarm detect/drain), 2 (pre-upgrade checks), 3 (backup), 4 (ordered stop),
5 (rpm upgrade), 7 (NVIDIA), 8 (ordered start + readiness polling), 9 (verification)
and 10 (Swarm reactivation) are unchanged apart from version strings.

### `clean-swarm-networks.sh` → v1.0.0 (new)

Standalone remedy carrying the former phase 4.5: data-root scrape from
`/etc/docker/daemon.json`, VXLAN interface teardown, `/var/run/docker/netns/*` purge,
`<data-root>/network/files/local-kv.db` removal, `docker_gwbridge` teardown.

Run standalone it cannot assume services are already stopped, so it wraps the
cleanup with its own ordered stop/start and a confirmation prompt describing exactly
what will be destroyed.

Indicated when a node returns from upgrade but cannot attach to overlay networks, or
logs "failed adding service binding". Added to the bundle script list and to README
troubleshooting.

### `rollback-docker.sh` → v2.0.0

Retargeted to 29.1.5 / 2.2.1 — banners, glob patterns, verification expectations.

Phase 3's config handling changes. A 2.2.6 → 2.2.1 downgrade needs no config change
(both use config v3, and the 2.2.1 loader logs unknown keys rather than refusing to
start), so there are three branches:

1. A backup exists and differs from the current config → restore it, saving the
   current one as `config.toml.pre-rollback`.
2. No backup, but a config exists → **leave it alone.** This is the case where the
   old code regenerated a default, and regenerating is the same hazard phase 6 of the
   upgrade script avoids.
3. Neither exists → generate a default, since there is nothing to preserve.

When several `/root/docker-backup-*` directories exist, the newest is used and all of
them are listed, because the newest is not necessarily the one belonging to the
upgrade being rolled back.

The closing note about losing the custom-bridge DNS fix is now false (29.1.5 has that
fix) and is replaced with an accurate statement of what rolling back forfeits.

### `download-docker-packages.sh` → v2.0.0

Four download loops retargeted. The rollback loops fetch 29.1.5 / 2.2.1 instead of
28.5.1 / 1.7.29. `clean-swarm-networks.sh` added to the bundled script list.

### `simulate-upgrade.sh`

Installs 29.1.5 / 2.2.1 as the simulated starting state and upgrades to
29.6.2 / 2.2.6. The `containerd config migrate` step is removed — there is no format
change to migrate across.

Retains the `createrepo` + `dnf install` + `distro-sync --allowerasing` strategy. This
remains deliberately a **different code path** from `upgrade-docker.sh`'s
`rpm -Uvh --force`, so a passing simulation still does not prove the air-gapped path
works. Per repo convention it carries no `VERSION` constant.

### `README.md` / `CLAUDE.md`

Version tables, verification commands, directory layout, and rationale updated. The
tarball name inconsistency is fixed: `download-docker-packages.sh` produces
`/opt/docker-upgrade-bundle.tar.gz`, and README is corrected to match (it currently
says `docker-offline-packages.tar.gz`).

### `recover-dnf.sh` — unchanged

Contains no version constants. Stays at v1.2.1; per repo convention script versions
drift on purpose.

## Operational notes

**The whole-cluster-together rule relaxes for this upgrade.** 29.1.5 and 29.6.2 both
speak containerd 2.2.x gRPC, so a mixed 29.1.5/29.6.2 Swarm will not produce the ALPN
handshake errors a mixed 1.7/2.2 cluster did. Nodes can be rolled one at a time. The
"upgrade together" guidance is retained in documentation for the 1.7 ↔ 2.x boundary.

**cgroup v1 is deprecated as of Docker 29.0.0**, with support continuing through May
2029. RHEL 8 defaults to cgroup v1; RHEL 9 defaults to v2. Not blocking for this
upgrade. Documented in README; no node configuration is changed.

**containerd 2.2.0+ is mandatory** for docker-ce after 29.2.0. 2.2.6 satisfies this.

## Validation

Static, runnable on the macOS dev machine:

- `bash -n` on all six scripts
- `shellcheck` on all six scripts
- Confirm every pinned RPM URL resolves on `download.docker.com` (upgrade set and
  rollback set, el8 and el9)

Dynamic, requires a RHEL VM and cannot run on the dev machine:

- `simulate-upgrade.sh` end to end
- Verification that a node with a relocated containerd `root` survives phase 6
  with its config intact — the specific regression this design exists to prevent

A full test plan is produced separately and reviewed before execution.
